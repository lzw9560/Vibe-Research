# 开发流程开销评估报告

> 日期：2026-08-04
> 范围：评估 `AGENTS.md` 约定的开发规范（spec → plan/tasks → feature 分支 → 实现 → review → 验收 → 归档 → squash 合并）对单一功能完成周期的影响，判断是否过重、如何精简。
> 状态：评估报告（仅留档，**不改动 AGENTS.md**）。若采纳精简建议，需另行立项变更。

---

## 1. 背景

`AGENTS.md`（2026-07-31 落地）为全仓库 agent 统一了"feature 分支 + 验收门 + grill 合并门 + squash"的开发流程，起因是此前多会话并行 commit 导致历史 interleaved 与工作树 entangle 事故。流程本身是对事故的响应，方向正确；但落地两个月（93 commits）后需要复盘：**流程对单一功能完成周期的拖累是否已经超过其防事故价值**。

## 2. 证据

### 2.1 commit 总量与结构（2026-07-01 起，develop 分支，93 commits）

| 类型 | 数量 | 占比 | 说明 |
|---|---|---|---|
| feat | 38 | 41% | 功能实现（产出） |
| docs | 25 | 27% | spec/plan/tasks、验收报告、归档标注等 |
| fix | 18 | 19% | 含 code review 修复、防封、假绿修复 |
| chore | 7 | 8% | |
| refactor | 4 | 4% | |
| test | 1 | 1% | |

docs 占 27%、fix 中相当部分为 review 往返修复——**约三成提交不直接产生功能**。

### 2.2 提交节奏

- 07-10 → 07-26：稀疏（日均 2 / 1 / 1 / 6 / 4 / 2 / 7）
- 08-01：爆发 23 条；08-02：18 条；08-03：6 条；08-04：10 条

周期内集中在 08-01/02 补验收与收尾动作（reaccept、归档标注），说明**大量验收/归档动作被推迟到事后批量补做**，而非按 spec 完成即时执行。

### 2.3 spec 规模分布

`specs/` 共 25 个 spec 目录（S001–S026，缺 S021）。spec.md 篇幅差异大：

- 小 spec（S022 熔断器修复，53 行）
- 中 spec（S023 漏斗可用性 84 行、S024 拓扑展示 76 行）
- 大 spec（S025 补前端入口 100 行、S026 pre-market-async 126 行）

其中 **S026 写了 126 行 spec，最终工作并入 S023 实现**（squash 合并 `ed0a0fe`）——为"形式完整"而生的 spec 白写一例，spec 篇幅与产出不必然正相关。

### 2.4 验收报告缺口（核心问题）

AGENTS.md 规定：**每个 spec 完成、提交前必须跑 playwright-pro 验收，报告落 `reports/acceptance/`，验收未过 = 硬阻**。

实际 `reports/acceptance/` 仅 3 份：

| 报告 | 内容 |
|---|---|
| S002-2026-08-02-reaccept-pass.md | 68 passed + 6 subtests |
| S016-2026-08-01-playwright-pass.md | 3/3 |
| S020-2026-08-01-offline-pass.md | 27/27（含真实降级测试） |

25 个已实现 spec 只有 3 份验收报告 → **验收门被普遍绕行**。两个后果：

1. 流程规定的"硬阻"实际没有执行，规范信任度受损；
2. 验收可信度实际靠人工 code review 兜底（从 commit 可见 `fix(S024): code review 2 HIGH + 防封 + 假绿`、`fix(S025): code review 3 核心 MEDIUM + 3 关键测` 这类"review 发现问题 → 修 → 再 review"多轮往返）。

### 2.5 单一 spec 的流程关卡（现状）

从 commit 前缀 + spec 头部归纳，一个 spec 完整走完约 8 道关：

1. `spec.md`（问题/目标/背景/关联）
2. `plan.md` + `tasks.md`
3. feature 分支（本地，不 push）
4. 实现（勤 commit）
5. 测试
6. code review（HIGH/MEDIUM 多轮）
7. 验收报告（playwright-pro，落 `reports/acceptance/`）
8. §0 归档标注（docs 提交）→ squash 合并 develop → 分支留 90 天

对小 spec（如 S022 熔断器 53 行修复），8 道关卡明显过重。

## 3. 问题诊断

| # | 问题 | 证据 | 成本 |
|---|---|---|---|
| 1 | **验收门被绕行** | 25 spec 仅 3 份报告 | 规范形同虚设，防回归承诺未兑现 |
| 2 | **一刀切流程** | 53 行修复与 126 行 spec 同走 8 关 | 小改动被强制承担大流程 |
| 3 | **review 多轮往返** | code review 2 HIGH / 3 MEDIUM 多次修复提交 | 单功能周期被 review 拉长 |
| 4 | **文档前置过重** | plan/tasks 独立成档；S026 spec 白写 | 形式完整 > 产出 |
| 5 | **验收/归档事后补做** | 08-01/02 集中 41 条提交 | 收尾动作积压，节奏失真 |
| 6 | **归档流程碎片化** | S023/S024/S025 各一条归档 docs 提交 | 3 条 docs 提交只做标注 |

根因：**流程按"最大 spec"的复杂度设计，未按 spec 规模分级；且关卡设置重"形式留痕"轻"风险控制"。**

## 4. 精简建议（按收益排序）

### 建议 1：分级流程（核心，收益最大）

按 spec 规模分三档，关卡随规模伸缩：

| 档位 | 判定 | 流程 |
|---|---|---|
| **small** | 单文件级修复、无 UI、无外部源（如 S022） | 只需后端 API 冒烟或单测；免验收报告、免归档标注、免 plan/tasks |
| **medium** | 当前多数 spec（S023/S024/S025 量级） | 验收报告简化为**单表**（PASS/FAIL 计数 + 环境 + 测试命令），归档并入 squash 合并 commit，不单开 docs 提交 |
| **large** | 跨系统、接外部源、有 UI（如 S020 worldmonitor） | 维持完整 playwright-pro 验收 + 完整报告 |

要点：**分级标准写入 AGENTS.md**，由 spec 作者在 spec 头部声明档位，grill/review 时校验档位匹配。

### 建议 2：review 单轮制

- 只阻断 **HIGH**；MEDIUM 记录进下轮 backlog，不阻塞提交。
- 明确"review 通过标准"（可运行、无 HIGH、验收符合档位），减少"修了再查、查了再修"的轮次。

### 建议 3：plan.md / tasks.md 合并进 spec.md

- 仅 **large** 必写独立 plan/tasks；medium 在 spec.md 内以章节呈现；small 不写。
- 消除 S026 式"为形式写文档"。

### 建议 4：验收报告最小化 + 批量归档

- medium 档验收报告单表化后，成本约降 80%，验收门可真正执行。
- §0 归档标注改为**批量**（如每周一次），不再每 spec 一条 docs 提交。

### 建议 5（可选项）：验收门软硬分层

- "硬阻"仅对 large 档强制；small/medium 未过验收 = 自动降级标记为 `needs-acceptance`，在 spec 目录标注待办，而非阻塞合并。避免"门太高 → 全绕行"的现状。

## 5. 落地选项与取舍

| 选项 | 做法 | 取舍 |
|---|---|---|
| A（推荐） | 采纳建议 1–4，修改 AGENTS.md 分级流程 | 需一次规范变更 + 存量 spec 档位回填；后续周期显著缩短 |
| B | 仅改建议 1（分级）+ 建议 2（单轮 review） | 改动最小，解决 80% 开销 |
| C | 维持现状 | 开销持续，验收门继续形同虚设 |

**预期收益（若采纳 A）**：small/medium 档 spec 关卡从 8 道降至 4–5 道，docs 类提交占比从 27% 显著下降，验收门从"被绕行"转为"低成本可执行"，单一功能完成周期预计缩短 30–50%。

## 6. 附注

- 本报告仅评估流程开销，不涉及"是否该走 feature 分支 / squash"——这两项是对事故的合理响应，建议保留。
- 流程变更落地前，建议对存量 25 个 spec 做一次档位回填（可批量完成）。
